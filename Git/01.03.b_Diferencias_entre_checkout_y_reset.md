# Entender HEAD y las ramas en Git

Una de las claves para entender cómo funcionan comandos como  
`git checkout`, `git switch` o `git reset` es comprender la diferencia entre **HEAD** y **rama**.

---

# HEAD y ramas

En Git tanto **HEAD** como las **ramas** son punteros a commits.

| Elemento | Significado |
|--------|-------------|
| **HEAD** | puntero que indica en qué commit estamos trabajando actualmente |
| **rama** | puntero que indica el último commit de esa rama, si hubiesen commits posteriores en esa rama se considerarían huérfanos (no pertenecientes a la rama) |

Cuando trabajamos normalmente en una rama ocurre esto:

```
A --- B --- C --- D
                  ↑
                main
                HEAD
```

- la rama `main` apunta al último commit (`D`)
- `HEAD` apunta a la rama actual (`main`)

---

# Navegar por el historial

El comando `git checkout` históricamente ha servido para varias cosas.

Puede:

- mover **HEAD** a otra rama  
  → actualmente se recomienda usar:  

```
git switch <rama>
```

- restaurar archivos a su estado en un commit  
  → actualmente se recomienda usar:  

```
git restore <archivo>
```

- mover **HEAD** a un commit concreto del historial  
  → sigue siendo común usar:  

```
git checkout <commit>
```

Importante:

`git checkout` **no modifica el historial del repositorio**, es decir, **no mueve el puntero de la rama**.

---

# Mover la rama (reescribir historial local)

El comando:

```
git reset
```

**mueve la rama actual y, por tanto, también el puntero HEAD a otro commit.**

Esto significa que la rama pasa a apuntar a otro punto del historial.

---

# Ejemplos con commits

Imaginemos que tenemos este historial:

```
A --- B --- C --- D
                  ↑
                main
                HEAD
```

---

# Situación inicial

```
HEAD → D
rama → D
```

Estamos trabajando normalmente en la rama `main`.

---

# Caso 1: git checkout C

```
git checkout C
```

Resultado:

```
A --- B --- C --- D
            ↑
           HEAD

main → D
```

Situación:

- **HEAD está en C**
- **la rama sigue en D**

Esto se llama **detached HEAD**.

Significa que estamos **explorando el historial**.

Desde aquí podemos:

- revisar versiones antiguas
- probar el proyecto en ese punto
- crear una rama nueva

Ejemplo:

```
git switch -c nueva-rama
```
en este caso el commit D no perdería la referencia a main y Git no la eliminaría.

---

# Caso 2: commit en detached HEAD

Si hacemos un commit en este estado:

```
A --- B --- C --- E
            ↑
           HEAD

main → D
```

El commit `E` **no pertenece a ninguna rama**.

Si no creamos una rama, ese commit puede quedar **huérfano** y Git podría eliminarlo más adelante mediante el **garbage collector**.

---

# Caso 3: git reset B

Si ejecutamos:

```
git reset B
```

Resultado:

```
A --- B --- C --- D
      ↑
    main
    HEAD
```

Ahora:

- **HEAD está en B**
- **la rama también está en B**

Los commits `C` y `D` dejan de formar parte de la historia de la rama.

Se denominan **commits huérfanos (dangling commits)**.

Estos commits **no se eliminan inmediatamente**, pero Git podría eliminarlos más adelante si ninguna referencia apunta a ellos.

---

# Idea clave para entender Git

Una forma útil de pensar en Git es la siguiente:

```
branch = puntero a commit
HEAD = puntero al commit actual
```

Por tanto:

```
git checkout → mueve HEAD
git switch → cambia de rama
git reset → mueve la rama
```

---

# Resumen visual

```
Historial inicial

A --- B --- C --- D
                  ↑
                main
                HEAD


Después de git checkout C

A --- B --- C --- D
            ↑
           HEAD

main → D


Después de git reset B

A --- B --- C --- D
      ↑
    main
    HEAD
```
